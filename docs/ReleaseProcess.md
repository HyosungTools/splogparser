# Release Process

This document describes how to perform a release of `splogparser`. Changes reach `main` through the [Pull Request Process](./PullRequest.md); this document covers shipping what's on `main`.

## 🚧 Workflow Summary

- **Prereleases**: automatic on every merge to `main` (`.github/workflows/build.yml`)
- **Releases**: manual, when there's enough on `main` worth shipping (`.github/workflows/release.yml`)

## 🔢 Versioning

Versions follow semantic versioning: `MAJOR.MINOR.PATCH`.

- **Prereleases** are numbered automatically by GitVersion (`GitVersion.yml`). After a release `v8.4.0`, the next merge to `main` produces `v8.4.1-prerelease.1`, then `-prerelease.2`, and so on.
- **Releases** are numbered by you when you run the workflow. Choose:
  - **PATCH** (`8.4.0` → `8.4.1`): only fixes
  - **MINOR** (`8.4.0` → `8.5.0`): new Views, worksheets or features
  - **MAJOR** (`8.x` → `9.0.0`): breaking changes to command-line usage or output layout

Once the release tag exists, GitVersion picks it up and prerelease numbering restarts from it.

## ✅ Before You Release

1. **Review the PRs merged since the last release.** On GitHub, compare the last release tag to `main`, or filter closed PRs by merge date.
2. **Tidy titles and labels.** Every PR title should read as a support-team release note, and every PR should carry a label. See the label table in [Pull Request Process](./PullRequest.md).
3. **Preview the notes (optional).** Go to **Releases > Draft a new release**, choose any new tag name, set the previous tag to the last full release, and click **Generate release notes**. Check the result, then **discard the draft**; don't publish it.
4. **Confirm the latest `build` run on `main` is green.** The release workflow re-runs the unit tests, but it's quicker to catch a failure here.

## 🔁 Release Steps

1. Go to **GitHub > Actions > Manual Release**.
2. Click **Run workflow**.
3. Enter the version **without** the `v` prefix, e.g. `8.5.0`.
4. The workflow will:
   - Check the version is `MAJOR.MINOR.PATCH`, the tag doesn't already exist, and the workflow is running from `main`
   - Write the version into `src\splogparser\VersionInfo.cs` (in the build only; this is not committed)
   - Build `splogparser.sln` in Release and run the unit tests
   - Build the Inno Setup installer
   - Zip the `dist` folder as `splogparser-<version>.zip`
   - Create and push tag `v<version>`
   - Create the GitHub Release `splogparser v<version>`, marked **Latest**, with both assets attached
   - Generate release notes from every PR merged since the previous **full** release (prereleases are skipped)

## 📄 Where the Release Notes Come From

The notes are generated by GitHub, not written by hand:

| Part of the notes | Comes from |
|-------------------|-----------|
| Section headings (🐛 Parsing Fixes, etc.) | PR labels, mapped in `.github/release.yml` |
| Each bullet | The PR title, author and number |
| Missing PRs | PRs labelled `internal` or `ci` are excluded |
| Full Changelog link | Previous full release tag → new tag |

To change the notes after release, fix the PR titles and labels, then edit the release on GitHub.

## 📦 Release Assets

- `splogparser-<version>.zip`: contents of `dist`
- `splogparser-setup-<version>.exe`: Inno Setup installer

## 🔒 Permissions

You must have push access and GitHub Actions permissions to run this workflow.
